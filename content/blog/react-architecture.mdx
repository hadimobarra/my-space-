## What architecture is for

A good structure makes one thing cheap: changing your mind. When a requirement moves, how many files move with it? Two questions decide that more than any folder layout. Where does each piece of state live? And what may import what?

## Part one: state

### Start by not having any

The best state is none. If a value can be calculated from what you already have, calculate it:

```tsx {2}
// ❌ Two sources of truth that will disagree one day
const [visible, setVisible] = useState(rows);
useEffect(() => setVisible(rows.filter((r) => r.name.includes(query))), [rows, query]);

// ✅ One source, always right
const visible = rows.filter((r) => r.name.includes(query));
```

The effect version renders once with stale data before correcting itself. React's own guide, [You might not need an effect](https://react.dev/learn/you-might-not-need-an-effect), is mostly about this pattern.

### Then climb one step at a time

```embed
state-ladder
```

- **Local state** for what only one component cares about: an open menu, an input's draft.
- **Lifted state** when siblings need it. Move it to the nearest common parent, no higher.
- **The URL** for anything a user would want to share or keep after a reload: filters, tabs, the selected row.
- **A server cache**, such as [TanStack Query](https://tanstack.com/query/latest), for data that belongs to the server. Copying it into your own store makes you responsible for its freshness.
- **A global store** for what is truly global and truly yours: the session, the theme, an unsaved draft across pages.

The URL is the most underused step. Filters in the URL bring back, forward, bookmarks and shared links for free.

### Make impossible states impossible

Four booleans describe sixteen combinations, most of them nonsense. A union describes only the real ones:

```ts
type Upload =
  | { status: "idle" }
  | { status: "uploading"; progress: number }
  | { status: "failed"; reason: string; retry: () => void }
  | { status: "done"; url: string };
```

You can't read `progress` from a failed upload, and the compiler lists every place to update when you add "paused". The [contact form](https://github.com/hadimobarra/my-space-/blob/main/components/sections/contact-form.tsx) on this site is a small real example.

## Part two: boundaries

### Organize by feature

Folders named after *kinds* of files spread each feature over the whole tree. Deleting one means a treasure hunt.

```text
src/
  features/
    catalog/
      api.ts          requests and response validation
      catalog.ts      domain types and pure logic
      SearchPanel.tsx
      index.ts        the public surface
    glossary/
  shared/             no knowledge of any feature
    ui/
    lib/
```

Two rules hold this up. Features don't import each other's internals, only their `index.ts`. And `shared` never imports a feature. Let a linter enforce both, because a rule that lives in a wiki lasts about a month:

```js title="eslint.config.mjs"
"no-restricted-imports": ["error", {
  patterns: [{
    group: ["@/features/*/*"],
    message: "Import from the feature's index instead.",
  }],
}],
```

### Keep logic out of components

A component is a hard place to test and an easy one to grow. Put decisions into plain functions:

```ts title="features/catalog/catalog.ts"
export function canEdit(entity: Entity, user: User): boolean {
  return user.isAdmin || entity.owners.some((o) => o.id === user.id);
}
```

Now the rule has a name, a test without rendering, and one home. When permissions become data rather than code, only this function changes.

### Validate where data enters

Types describe what you *hope* the server sends. Check it once, in `api.ts`, and the rest of the feature can rely on it. [Never trust JSON.parse in a render](/blog/never-trust-json-parse-in-render/) shows what happens otherwise.

### Prefer composition to configuration

A component that grows a prop for each new case ends up with thirty. Let callers assemble the parts:

```tsx
// ❌ Every variation is another prop
<DataTable showSearch searchPlaceholder="…" showExport exportFormats={["csv"]} footerText="…" />

// ✅ The caller decides what's inside
<DataTable rows={rows}>
  <DataTable.Toolbar>
    <Search />
    <ExportButton formats={["csv"]} />
  </DataTable.Toolbar>
  <DataTable.Body />
</DataTable>
```

With server components, composition matters even more: passing `children` through a client component is how server-rendered content stays on the server. See [the mental model](/blog/react-server-components-mental-model/).

## Container and presentational components?

Older guides, including an earlier version of this one, recommended splitting every component into a "container" and a "presentational" half. Hooks made that ceremony unnecessary: a custom hook separates the logic without a wrapper component. Its author [says the same](https://medium.com/@dan_abramov/smart-and-dumb-components-7ca2f9a7c7d0). Keep the idea, separate deciding from drawing, and drop the pairs of files.

## What to test

| Layer | Tool | Why |
|---|---|---|
| Pure logic | Unit tests | Fast, many cases |
| A feature | Testing Library | What the user sees and does |
| Critical paths | Playwright | The real browser, the real build |

If logic is in plain functions, the first layer covers most of the risk at the lowest price.

## Conclusion

Put state as low as possible and lift it only when something breaks. Give every feature an edge, and let a tool guard it. The folder names can be whatever you like.
